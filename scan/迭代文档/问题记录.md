## 二、语音识别 (Whisper)

### 4. ffmpeg 未安装导致音频下载失败  `发生: ~2026-06-01` `解决: ~2026-06-01`

**现象**：`yt_dlp.utils.PostProcessingError: ffprobe and ffmpeg not found`

**根因**：下载配置中指定了 `FFmpegExtractAudio` 后处理器，但 Windows 未装 ffmpeg。

**解决**：去掉后处理器，直接下载原生音频格式（m4a/webm），faster-whisper 用内置 av 库解码。格式优先级：`bestaudio[ext=m4a]/bestaudio[ext=webm]/bestaudio/best`。

**改动文件**：`src/transcriber.py`

### 5. Path.rmdir() missing_ok 报错  `发生: ~2026-06-01` `解决: ~2026-06-01`

**现象**：`TypeError: Path.rmdir() got an unexpected keyword argument 'missing_ok'`

**根因**：Python 版本兼容性问题。

**解决**：用 `try/except OSError` 替代 `missing_ok=True`。

**改动文件**：`src/transcriber.py`

### 6. CPU 语音识别太慢  `发生: ~2026-06-01` `解决: ~2026-06-02`

**现象**：medium 模型 26 分钟视频转录需 ~25 分钟。

**根因**：模型太大，纯 CPU int8 推理。

**解决**：逐步优化：
1. 模型 medium → small → tiny（精度换速度）
2. `beam_size=5 → 1`（贪心解码）
3. `vad_filter=True`（跳过静音段）
4. 最终：GPU 自动检测 `small + cuda + float16`，CPU 回退 `tiny + int8`

**改动文件**：`src/transcriber.py`

---

### 7. GPU 检测到但无法使用 (cublas64_12.dll)  `发生: ~2026-06-01` `解决: ~2026-06-01`

**现象**：`RuntimeError: Library cublas64_12.dll is not found or cannot be loaded`

**根因**：CUDA Toolkit 13.3 系统中的 cuBLAS DLL 版本不匹配，CTranslate2 需要 CUDA 12 的 `cublas64_12.dll`。`nvidia-cublas-cu12` pip 包已安装该 DLL 到 site-packages，但 Python 的 `os.add_dll_directory()` 对 C 扩展模块无效。

**解决**：在模块顶层（`import faster_whisper` 之前）用 `os.environ["PATH"]` 注入 nvidia 各包的 bin 目录。同时检测系统 CUDA Toolkit 路径。

**改动文件**：`src/transcriber.py` — `_inject_cuda_path()` 函数

---

### 8. int8_float16 在 CPU 上不支持  `发生: ~2026-06-01` `解决: ~2026-06-01`

**现象**：`ValueError: Requested int8_float16 compute type, but the target device or backend do not support efficient int8_float16 computation`

**根因**：混合精度仅特定 CPU 支持。

**解决**：`_get_model()` 中按 `("int8_float16", "int8")` 顺序尝试，失败自动降级。

**改动文件**：`src/transcriber.py`

### 9. temperature=0.0 导致转录循环重复  `发生: ~2026-06-02` `解决: ~2026-06-02`

**现象**：英文视频被识别成"好,所以我們現在在這裡..."循环 14 次。

**根因**：`temperature=0.0` + `beam_size=1` 使 softmax 分布过于尖锐，Decoder 陷入循环。

**解决**：去掉 `temperature=0.0`，保留 `num_workers=2` 和 `word_timestamps=False` 两个安全优化。

**改动文件**：`src/transcriber.py`

### 11. 12 小时长视频解析失败  `发生: ~2026-06-02` `解决: ~2026-06-02`

**现象**：长视频无响应或超时。

**根因**：Map-Reduce 固定只切 4 块，每块超大；块摘要 token 只有 1024；无进度反馈；SSE 超时 300s。

**解决**：
- 动态分块：~15K 字/块，最多 12 块
- >6 块时双层 Map-Reduce
- 块摘要提升至 2048 token
- SSE 超时延长至 900s
- 新增进度回调推送分段进度

**改动文件**：`src/analyzers/summarizer.py`, `src/web/server.py`

## 四、格式化与编码

### 12. Unknown format code    'd' for object of type 'float'

**现象**：`f"{4.0:02d}"` 崩溃。

**根因**：yt-dlp 返回的 `duration` 是 float，`divmod(float, 60)` 返回 `(15.0, 4.0)` 浮点数，`:02d` 要求 int。

**解决**：所有 `divmod(x, 60)` 前加 `int()`；extractor 中 `duration=int(info.get("duration", 0) or 0)`。

**改动文件**：`src/output/markdown.py`, `src/extractors/youtube.py`, `src/extractors/bilibili.py`, `src/web/server.py`

### 25. Bilibili 412 Precondition Failed（三轮定位）  `发生: 2026-06-03` `解决: 2026-06-04`

**现象**：解析 Bilibili 视频报 `ERROR: [BiliBili] ...: Unable to download webpage: HTTP Error 412: Precondition Failed`

**第一轮 — UA/Cookie/WBI 签名**（未解决）

以为 Bilibili API 全面要求 cookie → 添加 4 个 UA 轮换、412 指数退避重试、WBI 签名、cookie 文件加载、yt-dlp 也传 cookie。

实际测试发现：`httpx` 打 `api.bilibili.com` 的 REST API **一直返回 200**，并非 412 来源。

**改动文件**：`src/extractors/bilibili.py`, `src/config.py`, `src/web/server.py`, `src/transcriber.py`

**第二轮 — extract() 抛异常丢掉元数据**（解决部分问题）

发现视频无 CC 字幕时 `_fetch_subtitles()` 抛 `RuntimeError`，导致 `extract()` 终止并把已拿到的元数据（title/author/duration）全扔了。server.py 的 `except` 降级到 yt-dlp 做元数据提取，yt-dlp 抓 HTML 页面被 412 拦截。

修复：`extract()` 内 `try/except RuntimeError` 捕获字幕失败，返回空字幕但保留完整元数据。server.py 的 yt-dlp 降级路径也加 try/except 兜底。

**改动文件**：`src/extractors/bilibili.py`, `src/web/server.py`

**第三轮 — transcript.py 的 yt-dlp 音频下载**（真正根因）

前两轮后 412 仍出现。逐环节测试确认：

| 步骤 | 端点 | 方式 | 结果 |
|------|------|------|:--:|
| 视频元数据 | `x/web-interface/view` | httpx | 200 OK |
| 字幕信息 | `x/player/v2` | httpx | 200 OK（但无CC字幕）|
| **音频下载** | **`www.bilibili.com/video/...`** | **yt-dlp** | **412** |
| 流媒体 URL | `x/player/playurl` | httpx | 200 OK → DASH 音频流 |

真正根因：yt-dlp 试图抓取 `www.bilibili.com` HTML 页面获取视频信息时被 412，而 Bilibili 的所有 REST API（`api.bilibili.com`）通过 httpx + 浏览器 UA 可以正常访问，且 `playurl` API 直接返回 DASH 音频流 URL。

修复：`transcriber.py` 中 `download_audio()` 检测 Bilibili URL → 调用 `fetch_bilibili_audio_url()` 通过 `playurl` API 获取 DASH 音频直链 → httpx 流式下载（带进度），完全绕过 yt-dlp。

**改动文件**：`src/extractors/bilibili.py`（新增 `_BILI_API_PLAYURL`、`fetch_bilibili_audio_url()`）, `src/transcriber.py`（新增 `_download_bilibili_audio()`）

### 27. st_mtime 被覆盖导致历史记录时间错乱  `发生: ~2026-05-30` `解决: 2026-06-05`

**现象**：5 条历史记录在 Web UI 上全部显示 2026-06-05 01:23，但文件夹内文件的原始日期不同。

**根因**：`history` 端点用 `overview.md` 的 `st_mtime`（文件修改时间）作为时间戳。`st_mtime` 不可靠——某些进程重写了 5 个 `overview.md`，导致 mtime 被覆盖为相同值。分辨率精确到毫秒（.177 → .181 → .183 → .185），符合循环写入特征。

**解决**：
1. 分析完成时在 `meta.json` 中持久化 `created_at` 字段
2. `history` 端点优先读 `meta.created_at`，回退到 `st_mtime`
3. 已对所有现存记录回填 `created_at`（使用 Windows 文件创建时间 `st_ctime`）

**改动文件**：`src/web/server.py`

### 31. 批量解析资源竞争导致 GPU 空闲 CPU 满载  `发生: 2026-06-05` `解决: 2026-06-05`

**现象**：播放列表批量解析时 CPU/内存 100%，GPU 0% 占用。12 个 yt-dlp 下载同时启动，Whisper 全部回退到 CPU。

**根因**：批量启动时所有视频线程同时运行，GPU 显存不足以同时跑多个 medium 模型，全部 fallback 到 CPU int8。

**解决**：
1. 批量解析改为串行执行 — 一次只处理一个视频
2. `_model_lock` 双检锁保证 Whisper 模型只加载一次
3. 每个视频完成后才启动下一个

**改动文件**：`src/web/server.py`、`src/transcriber.py`

### 32. 内容归类策略被否决需按 Author_Date 重分组  `发生: 2026-06-09` `解决: 2026-06-09`

**现象**：用户要求撤销按内容领域分类，改为按 `作者_解析日期` 子文件夹归纳。

### 49. 超长视频转录峰值内存过高（OOM 风险）  `发生: 2026-08-30` `解决: 2026-09-14`

**现象**：2 小时以上的长视频解析时内存持续攀升，接近/触及 OOM；而短视频无此问题。

**根因**：Whisper 转录一次性把整段音频特征载入，音频越长峰值内存越高，与模型大小无关。

**解决**：**长音频分段转录**——按时长阈值切段逐段转录再拼接：
- `whisper_chunk_seconds: int = 600`（超过 10 分钟即切段）
- `whisper_chunk_overlap: float = 2.0`（相邻段重叠 2 秒，防止边界截断丢字）

实测（2h52m 视频）：峰值 mem_used 2.96GB，全程 swap 零增长，46 分钟跑完。

**改动文件**：`src/transcriber.py`, `src/config.py`

### 50. RAG 索引常驻内存 ~1.6GB  `发生: 2026-09-14` `解决: 2026-09-14`

- 默认关闭，省 ~1.6GB 常驻内存，whisper + LLM 主流程不受影响
- 需要检索时改 True + 重启即可恢复

### 51. faster-whisper 模型任务后不释放  `发生: 2026-09-14` `解决: 2026-09-14`

`Refused to load the image 'http://iX.hdslb.com/...' because it violates the following
Content Security Policy directive: "img-src ..."`。

**取证（四层，全部实测）**：

| 层 | 检查 | 结果 |
|---|---|---|
| 前端 | 线上页是否含 `referrerpolicy="no-referrer"` | ✅ 在（2 处）—— 上一次 Referer 403 修复已上线 |
| API | `GET /api/history/{base}` 是否下发 thumbnail | ✅ 下发；但 scheme = **`http`** |
| 图床 | 20 张封面 URL 真实可达性 | ✅ 20/20 **http、https 双通**（206）→ 图没死 |
| 安全头 | 线上响应头 CSP（Caddy `scan` 段） | `img-src 'self' data: https://*.hdslb.com https://*.ytimg.com` → **只放行 https** |

**根因**：B 站 `view` 接口的 `pic` 字段本身就返回 `http://iX.hdslb.com/...`，
`bilibili.py` 原样存进 `meta.json`；页面是 https，CSP 的 scheme-source 是**严格 scheme 匹配**，
`http://` 不匹配 `https://*.hdslb.com` → 拒载。
附带问题：`http://` 图在 https 页属 mixed content，Firefox 直接拦、Chrome 会自动升级 ——
**同一份页面在不同浏览器表现不一致**，靠浏览器行为兜底不算修复。

**解决（甲方案）**：
- 新增 `src/urlutil.py::https_url()`（空值/`http://`/协议相对 `//` 一律规整，其余原样）；
- 入库端：`bilibili.py`、`youtube.py` 取封面即归一；
- 出库端：`history.py` 读 `meta.json` 时归一（**存量记录零重解析即生效**）；
- 实时链路：`pipeline.py` 两处（API 提取 / yt-dlp 兜底）归一；
- 导出：`html_standalone.py` 归一（独立 HTML 同受益）；
- 前端：`setThumb()` 再兜一层 `http→https`（`index.html`）。

**为什么不动 CSP**：给 `img-src` 补 `http://*.hdslb.com` 会降安全基线，且 mixed content 仍按浏览器
差异表现；加 `upgrade-insecure-requests` 只对浏览器生效，导出的独立 HTML 不受益。归一 URL 一招
同时解决「CSP 匹配」「mixed content」「导出页」三处。

**验证**：
- 单元层 `https_url` 边界 **9/9**；
- 静态层前端提升逻辑 + `no-referrer` **4/4**；

- 线上页（无 Referer）取图 `200 image/jpeg 314333 字节`，带本站 Referer 对照 `403`（防盗链仍在）。
- 回归总入口：**通过 11 / 失败 0 / 跳过 0**。

### 70. 单账号二元鉴权升级为三角色  `发生: 建站起` `解决: 2026-10-15（阶段 1）`

**现象/需求**：`auth.py` 只读一个账号的 bcrypt 哈希，中间件只有「游客白名单 / 管理员全放行」
两条分支；前端更是 `isAdmin(){ return !!getAuth(); }` —— **只要登录就是管理员**，
没法区分「能解析的普通用户」和「全权管理员」。

**解决**：
- 新增 `src/web/roles.py`：角色常量（`guest`/`user`/`admin`）、`member_allowed()`（常规用户
  路由白名单）、`can_view_record()`（行级可见性单一判据，供列表过滤/详情 404/导图 404 三处共用）；
- `auth.py` 改造：`load_accounts()` 支持**多账号**凭据文件（`账号:` 再次出现即新记录，
  键名中英皆可），中间件按角色分派并把 `user`/`role` 写进 `request.scope["state"]`
  （路由层靠它做归属判断）；新增 `GET /api/whoami`；
- 前端改为**角色驱动**：`isAdmin()` 依据 `/api/whoami`（不是「有凭据」），新增
  `isMember()`/`requireAdmin()`；对比、打包导出、批量解析按钮对常规用户直接从界面撤掉
  （与其点了吃 403，不如不给看）；
- 凭据兼容：**旧单账号文件零改动继续可用**（缺 `角色:` 行 = admin），改文件前自动备份；
- 管理工具 `/root/scripts/scan_accounts.py`（服务器本地，不入公开仓库）：
  `list` / `add <账号> --role user|admin` / `passwd` / `remove`，新账号明文密码只写
  `/root/.scan-user-cred`（0600），**脚本从不打印密码**，`remove` 拒绝删掉最后一个管理员。

**踩坑（值得记）**：
1. `scripts/verify/_common.py::load_cred()` 原来取的是**文件里最后一条**账号 —— 新增常规用户后，
   所有既有验收用例会**以常规用户身份**去跑管理员端点，全部 403 假失败。改为
   **默认取 `角色: admin` 的账号**，`SCAN_CRED_ACCOUNT=<账号>` 可指定其它账号。
2. 常规用户的**删除入口**：界面上只有「批量删除」一个按钮，若把它列为管理员专属，
   常规用户就等于**不能删自己的记录**（与其需求矛盾）。故 `batch_delete` 对常规用户放行，
   由路由层只删自己的（别人的进 `failed` 列表）——阶段 2 落地。
3. `bcrypt` 哈希对比对非 ASCII str 会抛 `TypeError`（老坑），多账号遍历同样用 bytes 比较。

**验证（实测）**：
- `verify_roles.py`（新增回归）**38/38**：解析层 5 例（含旧格式兼容、怪角色降级 `user`、
  缺哈希不生效）+ 规则层矩阵（常规用户 13 放行 / 5 拦截；可见性 5 记录 × 3 角色）+
  静态层 8 项（前端角色门控）+ API 层 18 项（三角色 `whoami`、游客 403、常规用户
  放行 422/拦截 403、管理员全放行、错密码 401）；
- 凭据文件改写后**原密码仍可登录**（旧备份明文 × 新文件哈希交叉校验，管理员与新增账号均通过）；
- 既有全量回归 **通过 11 / 失败 0 / 跳过 0**（未被打坏）；
- 线上重启后日志：`[auth] 已加载 2 个账号（角色：scanuser=admin,alice=user）`。

**改动文件**：`src/web/roles.py`（新增）、`src/web/auth.py`、`src/web/guest_rules.py`、

### 71. 行级可见性：常规用户建的记录不对游客公开  `发生: 需求提出 2026-10-15` `解决: 2026-10-15（阶段 2）`

**需求**：常规用户（外部账号）解析的记录，不该让**游客**看到；常规用户之间互看没问题
（用户拍板 ②：常规用户彼此可见）。管理员与存量记录维持公开。

**做法：一个判据，四处共用**
- 归属写入：`run_pipeline()` 新增 `owner` / `owner_role` 两个参数，落进 `meta.json`：
  `visibility = "members"`（常规用户建的）/ `"public"`（管理员建的、无归属的）。
  入口两处（`/api/analyze`、`/api/analyze/playlist`）从 `viewer(request)` 取账号与角色传入。
- 判据唯一：`roles.can_view_record(role, rec)` —— **无 `visibility` 时由 `owner_role` 推导，
  无 `owner` 的一律 public**（存量 36 条零迁移即兼容）。不允许各路由自己写一份。
- 落点四处：`GET /api/history`（列表**过滤掉**，不是灰掉）、
  `GET /api/history/{base}`、`GET /api/mindmap/{base}`、`GET /api/export/{base}`
  → 不可见一律 **404**（403 等于承认"这条记录存在但不给你看"）。
- 下载是文件路径（`记录名/overview.md`），可见性在目录的 `meta.json` 上 →
  新增 `history.meta_for_path()` **向上最多找 4 层**；找不到 meta 按 public 放行
  （路径安全仍由既有的 `resolve_within` 负责，两件事不混）。
- 删除按**归属**而非可见性：管理员全可删，常规用户只删 `owner == 自己`；
  批量删除里别人的记录**逐条进 `failed`**（整批 403 会让一次勾选全废）。
  前端同步：不可删的条目置灰复选框 + `🔒 不可删`，但**判定始终以服务端为准**。

**验证**：新增 `scripts/verify/verify_visibility.py`（45 项，全绿）。不跑真实解析
（要下载+转录，分钟级），而是**临时造一条带指定 owner 的记录**再穿 HTTP 层打三角色矩阵，
`finally` 删除、脚本末尾兜底清 `_verify_vis_tmp_*`（实测零残留）。覆盖：
列表可见性 / 详情 404 / 导图 404 / 下载 / 导出 / 删除归属 / `meta_for_path` 向上查找。

**已知边界（重要）**：
1. **导出 HTML 脱离站点后无法防转看** —— 文件一旦下载到本地，任何行级可见性都失效。
   同理，登录用户拿到的内容可以随手转发。可见性只挡"未登录的匿名浏览"。
2. 游客访问 `/api/download/` 是**白名单整段 403**，到不了路由的可见性 404；
   路由里那层是纵深防御（白名单哪天放宽仍拦得住），由单元层用例直接验证。
3. `meta.json` 现有 36 条**无 owner**，一律 public —— 无法追溯归属，属已接受的取舍。

### 72. 资源闸与常规用户日配额：OOM 的正面防御  `发生: 二期需求 2026-10-15` `解决: 2026-10-15（阶段 3）`

**背景**：`/api/analyze` 原来每条裸起线程、**无全局并发闸**；内存账是
常驻 2.0GB + 每条峰值 ~1.3GB，物理 3.9GB ⇒ **2 条并行 = 4.6GB，必炸**；
而 `MemoryMax=4G ≥ 物理 3.9GB` 等于没设，触顶是**全局 OOM**（内核乱杀，
历史上真杀过 hermes-gateway）。用户拍板：闸 = **2**、日配额 **100**、
口径 **(b) 按实际产出 + 失败返还**。

**三层防御，各管一件事（缺一不可）**
| 层 | 位置 | 管什么 | 默认 |
|---|---|---|---|
| 转录闸 | `_TRANSCRIBE_GATE`（原有） | 无字幕→whisper 那一段串行 | 1 |
| **全局流水线闸** | `_PIPELINE_GATE`（新增） | **同时**在跑的完整流水线上限 | 2 |
| 日配额 + 在飞名额 | `src/web/quota.py`（新增） | 每账号的**速率**与**并发** | 100/天、2 个 |

- 闸用 `await asyncio.to_thread(_PIPELINE_GATE.acquire, True, 2.0)` 轮询获取：
  直接 `acquire()` 会把 uvicorn 事件循环卡住，所有 SSE 进度流一起停顿（前端像"卡死"）。
  排队时推 `排队中：已有 N 条解析在跑...` 给前端。
- **只在真取到闸时释放**（`got_gate` 标志）：`Semaphore.release()` 多放一次会让闸失效。
- 缓存回放在**取闸之前** return ⇒ 回放不占闸、不计配额（没有产出）。

**配额口径为什么"提交时不预扣"**：预扣+事后返还看着更严，但本机 3.9GB 下进程被 OOM
杀掉是常态风险，预扣的条数永远还不回来（用户莫名丢配额）。**只在写出记录时 +1**，
进程崩了最多白送一次，绝不错扣。实现上 `produced = True` 紧跟在 `meta.json` 写盘之后，
`quota.settle(owner, produced)` 放在 `run_pipeline` 的 `finally` ⇒ 成功/异常/取消都会
还名额（失败返还）。

**顺序细节（踩过的坑）**：`/api/analyze` 里 **`claim_task` 在前、`quota.reserve` 在后** ——
① 同一 URL 重复提交应报 **409**（正在解析）而不是吃配额报 429；
② reserve 失败必须 `release_task(task_id)`，否则这个 URL 会被永久当成"在跑"。
E2E 用"同一 URL 连提两次都得 429 而非 409"来证明登记确实被释放了。

**验证**：
- `scripts/verify/verify_quota.py`（41 项，离线单元 + 静态接线 + 线上 whoami 字段）——
  覆盖在飞上限、产出计数、失败返还、用尽文案、落盘持久化（模拟重启读回）、管理员不限。
- `/root/scripts/scan_quota_e2e.py`（运维脚本，不入仓库）：改账本 → 重启 → whoami 剩 0 →
  提交得 **429「今日解析配额已用完」** → 同一 URL 仍 429（非 409）→ 恢复账本 → 重启 →
  剩余回到 100。**全绿**。
- 回归总入口 14/14。

**已知边界**：配额限的是"每个账号自己"，防不住**多账号**合起来压垮内存（那要靠全局流水线闸）；
闸=2 是按"单条峰值 1.3GB"估的，真实峰值待观察，超预期就退回 1。
