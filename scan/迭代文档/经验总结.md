# 项目经验总结

从零到完整可运行系统的全过程复盘。

---

## 一、架构设计

### 1. 管道架构是最正确的选择

```
提取 → 预处理 → 分析 → 翻译 → 输出 → RAG
```

每个阶段独立模块，输入输出通过统一数据模型（`SubtitleEntry` / `VideoMeta` / `AnalysisResult`）衔接。

**核心收益**：Whisper 转录的 `SubtitleEntry[]` 和 API 字幕的 `SubtitleEntry[]` 对后续管道完全透明——预处理、LLM分析、翻译不需要知道数据来源。这是回退机制能丝滑运作的前提。

### 2. 回退优于单点

不要赌一个方案能覆盖所有场景。三级回退（API → yt-dlp → Whisper）让系统在任何情况下都有底线输出。每个回退层有独立的错误类型和日志，上层无需关心下层实现。

### 3. 插件化提取器

`BaseExtractor` 抽象类 + `match()` / `extract()` 两个方法 + 注册器模式。加新平台只需一个文件，不碰核心管道。

### 4. 数据模型先于代码

项目启动第一步是定义 `models.py`。所有模块围绕同一套 dataclass 通信。先确定数据形状，再写逻辑。

---

## 二、本地 ML + 云端 LLM 的混合架构

### 5. 边界清晰

```
本地(免费): 字幕提取 + 音频下载 + 语音识别 + 向量嵌入
云端(API): 摘要生成 + 重点提取 + 翻译 + 问答
```

用户关心的核心性能（Whisper 速度）在本地可控调优；需要智能判断的部分（摘要质量）用最强云端模型。

### 6. GPU 检测要依赖对的东西

PyTorch 是 CPU 版不代表 CUDA 不可用。faster-whisper 底层是 CTranslate2（独立的 CUDA 推理引擎）。检测 GPU 应该用 `ctranslate2.get_cuda_device_count()` 而不是 `torch.cuda.is_available()`。

### 7. CUDA DLL 加载时机是关键

`os.add_dll_directory()` 只影响 `ctypes`，不影响已加载的 C 扩展。CTranslate2 的 CUDA 模块在 `import faster_whisper` 时加载，所以 DLL 路径必须在 import **之前**通过 `os.environ["PATH"]` 注入。这个顺序错了一切都白费。

### 8. Whisper 模型选择是速度-精度权衡

| 策略 | 参数 | 效果 |
|------|------|------|
| 模型大小 | tiny(39M) → small(244M) | 越大越准越慢 |
| beam_size | 5→1 | 贪心≈束搜索质量的95%，快3x |
| VAD | 关→开 | 跳过静音≈自动提速20-30% |
| word_timestamps | 开→关 | 去词级时间戳，少一轮decoder循环 |
| temperature | 默认→0.0 | **不要改**，会导致循环输出 |

安全优化项（已验证不损质量）：`num_workers=2`、`word_timestamps=False`、`vad_filter=True`、`beam_size=1`。

## 三、API 对接的坑

### 9. 第三方库 API 会静默变更

`youtube-transcript-api` 从 0.x 升到 1.x，`get_transcript()` 变成了 `list()` + `fetch()`。没有任何编译期提示，运行时才发现。

**教训**：启动时验证关键依赖的 API 签名，或者在 import 后立即做 smoke test。

### 10. LLM 响应格式不统一

DeepSeek 的 Anthropic 兼容端点返回 `ThinkingBlock`（type="thinking"）作为 content 第一条，真正的文本在后面的 `TextBlock`。直接 `r.content[0].text` 会崩溃。

**教训**：遍历 `r.content` 按 type 取值，不要假设第一个块就是文本。

### 11. LLM 输出需要 Schema 约束

`KeyPoint` 提取必须用 `json_schema` 约束输出格式。裸 prompt 返回的文本解析脆弱，一个多余的换行就破坏整体。`chat_json()` 函数专门处理 markdown code fence 剥离和 JSON 加载异常。

## 四、Python 类型陷阱

### 12. yt-dlp 返回数字是 float

`info.get("duration")` 可能返回 `904.0`（float）而非 `904`（int）。`divmod(float, 60)` 返回浮点数，`:02d` 格式化需要 int。

**教训**：所有外部来源的数字在格式化前统一 `int()`。

### 13. Windows 编码是隐形坑

终端 GBK 编码让所有中文输出变成乱码。不影响实际逻辑，但调试时非常困惑。

**教训**：调试输出用 `sys.stdout = io.TextIOWrapper(sys.stdout.buffer, encoding='utf-8')` 重定向。生产代码不受影响。

## 五、前端设计

### 14. SSE 优于轮询

视频分析是长时间异步任务。SSE 比 WebSocket 简单（单向推送即可），比轮询高效。5 种事件类型（status/download/transcribe/done/error）覆盖所有状态。

### 15. 长任务必须分段反馈

如果用户看到"分析中..."持续几分钟不动，会认为是卡死了。就算总时间不变，分步显示进度（"摘要: 3/8 段"、"重点提取: 5/8 段"）也能大幅改善体验。

### 16. CSS 自定义属性是主题切换的银弹

所有颜色通过 `var(--xxx)` 引用，主题切换只需覆盖 `[data-theme="light"]` 下的变量值。不改一行 HTML，加 15 行 CSS 就完成了 Light/Dark 模式。

## 六、调试方法论

### 17. 从末端反向追溯

当"该视频没有可用字幕"出现时，正确的排查路径是：
1. 确认是哪个提取器匹配了 URL → `get_extractor(url)`
2. 确认提取器的每一步返回了什么 → 直接调 `extractor.extract(url)` 看 `subs` 字段
3. 如果为空，单独测试 API → `curl` 或 Python 直接调底层库
4. 定位到具体异常 → 补日志、改错误处理

不要从 UI 开始猜，直接走代码路径。

### 18. 先复现再修

每次修 bug 前先用一个最小复现脚本确认问题存在、理解根因、验证修复。不要边猜边改。

### 19. 性能优化先测基准

Whisper 优化时每次都跑同一个 19 秒视频做 AB 对比。没有基准的优化是玄学。

## 七、可以做得更好的地方

### 20. 测试覆盖

当前零测试。对于提取器的 `match()`/`extract()`、预处理管道的每个步骤、语言检测逻辑，都应该有单元测试。至少要做：
- `clean()` 的 HTML 去除、繁简转换
- `deduplicate()` 的相似度阈值
- `segment()` 的分段逻辑
- `needs_translation()` 的 CJK 检测
- `_sanitize_task_id()` 的边界情况

### 21. 日志系统

当前只用 `print()`。应该有结构化日志（级别、时间戳、来源模块），方便排查生产问题。Whisper 的 `[Whisper] GPU detected → ...` 这种 print 应该走统一的 logger。

### 22. 配置管理

`ANTHROPIC_MODEL` 和 `ANTHROPIC_REASONING_MODEL` 写死在 `.env`。如果切换模型需要改文件。可以考虑在 Web UI 加入模型选择器（或至少用环境变量覆盖）。

### 23. 错误恢复

分析流程中任何一个阶段失败（比如 LLM 返回异常、Whisper 崩溃），整个任务终止。应该有中间结果保存和断点恢复机制。尤其是超长视频，跑了 30 分钟的 Whisper 转录后 LLM 调用失败，全部白费。

### 24. 并发处理

当前一次只能分析一个视频。如果用户粘贴第二个 URL 需要等第一个完成。FastAPI 本身支持多请求，但 SSE 和后台线程没有做任务队列管理。

## 八、提问技巧（给 AI 的有效指令）

### 25. 有效的提问模式

| 不好的提问 | 好的提问 |
|-----------|---------|
| "不行" | "错误: XXX，用这个 URL 测试的" |
| "加个功能" | "目标：XXX，交互方式：XXX，优先级：XXX" |
| "太慢了" | "26 分钟视频转录用了 25 分钟，设备 i5-11400H+RTX3050Ti" |

### 26. 先给上下文再给指令

有效的提问结构：
1. 当前状态（设备、环境、配置）
2. 期望效果（具体、可验证）
3. 约束条件（不损质量、不动某模块）

### 27. 验证后再推进

每完成一个功能模块立即用真实数据测试。不要攒到多个改动一起测——那时候定位问题极难。

## 九、近期迭代经验（2026-06）

### 28. 多轮定位要逐环节测试

Bilibili 412 问题的三轮定位是典型案例：

| 轮次 | 假设 | 实际 |
|------|------|------|
| 1 | Bilibili API 全面要求 cookie | httpx 打 API 其实一直 200，UA+WBI 不致命但有用 |
| 2 | extract() 抛异常触发 yt-dlp | 修复了元数据丢弃，但不是 412 来源 |
| 3 | download_audio 的 yt-dlp | **真正根因** — yt-dlp 抓 HTML 页面被 412，用 playurl API 直连替代 |

**教训**：错误信息里的 `[BiliBili]` 前缀说明错误来自 yt-dlp，应该第一时间追踪那个调用栈，而不是从提取器开始猜。每一层都要独立测试，不要假设"改了这一层就够了"。

### 29. 不要丢弃已获取的数据

`extract()` 中 `_fetch_info()` 成功获取了标题/作者/时长，但 `_fetch_subtitles()` 抛异常导致整个 extract 终止，元数据全部丢弃。server.py 降级到 yt-dlp 才触发真正的问题。

**教训**：管道中每一步成功获取的数据都不应该被后续步骤的失败丢弃。`try/except RuntimeError: pass` 一行修复了架构级的数据流缺陷。

### 30. 对外部服务同时保留多条路径

Bilibili 对 `www.bilibili.com`（HTML 页面抓取）和 `api.bilibili.com`（REST API）的反爬策略完全不同。前者 yt-dlp 被 412 拦截，后者 httpx 带浏览器 UA 正常返回。

**教训**：不要依赖单一入口。playurl API 获取 DASH 音频流直链的方案不仅绕过了 412，还比 yt-dlp 下载更快（直接 CDN 节点）。

### 31. Obsidian 集成只做文件级

路线一（YAML frontmatter + `[[wikilink]]` + Vault 直写）是零成本的集成方案。更深度的集成（Obsidian 插件）需要独立维护 TypeScript 代码库，边际收益递减。

**教训**：对第三方工具的集成，先做到它能"读取和识别"你的输出，而不是反过来让你的工具驱动它。文件系统是最终的接口。

### 32. 模型升级用回退链而非一刀切

medium 模型在 4GB 显存上刚好够，但不能假设所有环境都能跑。三级回退链（medium GPU → small GPU → small CPU）让升级零风险——medium 失败自动退到 small，不影响任何用户。

**教训**：任何性能/质量的提升都要配降级路径。`for model in [preferred, fallback]: try/except` 比 `if/else` 更安全。

### 33. 前端分组需要同时保留个体标签

D 方案（按路径折叠分组）解决了多仓库管理，但折叠后组内所有 item 看起来一样。A 方案的彩色路径标签让每个 item 保持独立标识。组合 A+D 后每个 item 有 path badge + 组头有 color，两者互补。

**教训**：UI 的"全局结构"（分组）和"局部标识"（标签）是两个独立需求，各需要自己的视觉元素。

### 34. Markdown 内容要防御性清洗

LLM 输出的 keypoint content 含 `\n` 和 `|` 字符，直接写入 markdown 表格会破坏格式。`content.replace("\n", " ").replace("|", "｜")` 两行代码从源头解决。

**教训**：任何外部来源（LLM、API、用户输入）的内容写入结构化格式（markdown 表格、JSON、CSV）前，必须做格式转义。不要假设 LLM 会遵守你的格式约束。

### 35. 解析器要对损坏数据保持兼容

即使修复了写入端，已有的损坏文件（旧版生成的 keypoints.md）也需要能正常解析。`pending` 状态机让解析器能处理换行拆分、缺列等异常格式。

**教训**：修复 bug 时同时考虑历史数据的兼容性。新写入的不会再坏，但已有的损坏文件要能自动修复读取。

### 40. 前端时间戳跳转用 `<a target="_blank">` 而非 iframe  `发生: 2026-06-05` `解决: 2026-06-05`

**需求**：点击重点标示/字幕中的 `[12:34]` 跳转到视频对应时间。

**方案对比**：

| 方案 | 复杂度 | 体验 | 实现 |
|------|:------:|:----|------|
| iframe 嵌入播放器 + `seekTo` API | 高 | 页面内跳转 | 需要 YouTube IFrame API + Bilibili embed SDK，跨域问题多 |
| `<a target="_blank" href="...?t=N">` | 低 | 新标签页打开 | 拼 URL 即可，平台原生支持 `?t=` 参数 |

**选型**：新标签页打开。原因：(1) 零维护，(2) 用户可自行选择播放器，(3) Bilibili 的 embed 方案不稳定。

**教训**：前端功能不要上来就想用 iframe/API 方案。先看最简单的 HTML 链接能否满足需求——URL 带时间戳参数是 YouTube 和 Bilibili 都原生支持的。iframe 方案虽然看起来更"集成"，但引入跨域、API 版本兼容、移动端适配等问题，收益远小于成本。

### 41. asyncio 并发改造要连带修改调用链签名  `发生: 2026-06-05` `解决: 2026-06-05`

**现象**：将 `summarize()` 和 `extract_keypoints()` 改为 async 函数后，调用处（`pipeline.py`）需要移除 `asyncio.to_thread` 包装，否则 `await async_fn` 在 thread 里运行会报错。

**教训**：Python 的 async 改造是"传染性"的——一个函数改为 async，所有调用它的地方都需要跟着变。先画清楚调用链再动手改。本项目中：
```
pipeline.py: await asyncio.to_thread(summarize, ...)
  → summarize() async def
  → _summarize_long() async def → asyncio.gather(chunks)
  → _summarize_short() via asyncio.to_thread (单个 LLM 调用)
```
改造后：
```
pipeline.py: await summarize(...)
  → summarize() 内部自动并行
```

### 42. Embedding 模型切换是破坏性变更  `发生: 2026-06-05` `解决: 2026-06-05`

**现象**：将 `all-MiniLM-L6-v2(384d)` 切换到 `BAAI/bge-m3(1024d)` 后，现有 ChromaDB 集合查询失败。

**根因**：ChromaDB 的每个 collection 在创建时就固定了 embedding 维度。切换模型后查询向量维度与存储向量维度不匹配。

**解决**：删除 `.chromadb/` 目录重建。

**教训**：Embedding 模型切换不是配置热更新，是破坏性变更。建议在项目早期、数据量不大时做。如果后续需要切换，必须设计迁移策略（双模型并行、渐进重建等）。bge-m3（1024 维，中英文 SOTA）是目前多语言场景的最佳选择，短期内不应再换。

### 36. 文件系统 mtime 不是可靠的数据源  `发生: 2026-06-05` `解决: 2026-06-05`

**现象**：5 条历史记录在 Web UI 上全部显示同一时间（2026-06-05 01:23），但实际分析时间不同。

**根因**：`overview.md` 的 `st_mtime`（文件修改时间）被某个进程覆盖为相同值。`st_mtime` 不可靠——git checkout、文件同步、脚本触碰、备份恢复都会修改它。

**解决**：在 `meta.json` 中持久化 `created_at` 字段，分析完成时写入一次，之后不再修改。`history` 端点优先读 `meta.created_at`，回退到 `st_mtime`。

**教训**：文件系统的元数据（mtime/ctime）不是应用层的数据存储。任何需要持久化的业务数据（创建时间、状态、分类）都应该显式写入自有文件（`meta.json`），不要依赖操作系统提供的文件属性。如果必须用文件属性做降级，优先用 `st_ctime`（Windows 上=文件创建时间）而非 `st_mtime`（修改时间）。

### 37. 用户可控路径必须 resolve 后校验  `发生: 2026-06-05` `解决: 2026-06-05`

**现象**：`/api/download/../../.env` 可以读取项目根目录的 `.env` 文件（含 API Key）。

**根因**：`Path(root) / filepath` 直接拼接用户输入的 `filepath`，`..` 可以从输出目录逃逸到任意系统目录。`download`、`delete_history`、`history_detail` 三个端点都存在同样问题。

**解决**：
```python
resolved_root = root.resolve()
fp = (resolved_root / filepath).resolve()
if not str(fp).startswith(str(resolved_root) + os.sep) and fp != resolved_root:
    continue
```

**教训**：任何接受用户输入文件路径的端点，必须经过两步校验：(1) `resolve()` 消除 `..` 和符号链接，(2) 确认解析后的路径仍在允许的根目录内。只在拼接前做 `../` 字符串检查是不够的——编码、符号链接、路径穿越变体都可以绕过。

### 38. FastAPI 模块拆分用 APIRouter 而非手动 import  `发生: 2026-06-05` `解决: 2026-06-05`

**现象**：`server.py` 从 521 行增长到包含路由、分析管道（180 行）、历史 CRUD 三个职责，难以维护。

**解决**：拆分为三个文件：
```
src/web/server.py   64 行  — 仅路由定义 + app 创建
src/web/pipeline.py 182 行 — 分析管道逻辑 + SSE 事件系统
src/web/history.py  196 行 — 历史 CRUD（使用 FastAPI APIRouter）
```
历史模块使用 `APIRouter()` 定义路由，`server.py` 通过 `app.include_router()` 挂载，无需手动导入每个函数再添加装饰器。

**教训**：FastAPI 项目规模增长时，按领域拆分到 `APIRouter` 文件是标准模式。不要在 `app` 所在文件里堆所有路由。拆分时机不是看行数，而是当你能明确说出"这部分是一个独立的职责"的时候。

### 39. 写测试能发现意想不到的行为边界  `发生: 2026-06-05` `解决: 2026-06-05`

为 5 个纯函数模块补充 79 个测试，过程中发现多处预期与实际行为不符：

| 模块 | 预期 | 实际 | 原因 |
|------|------|------|------|
| `_fmt_srt_time()` | `0.0005 → "00:00:00,001"` | `→ "00:00:00,000"` | Python `round()` 使用 banker's rounding，0.5 舍入到 0 |
| `_similarity("", "a")` | `1.0` | `0.0` | 空字符串不具有和非空字符串相同的字符 |
| `generate_srt()` 两条 | `lines[3] == "2"` | `lines[4] == "2"` | SRT 条目间有空行分隔 |
| `needs_translation("你好 world hello")` | `False` (50% CJK) | `True` (16% CJK) | CJK 计数 2/12 非空格字符=16%，低于 30% 阈值 |

**教训**：测试不是为了验证代码正确（那是在讨好已有实现），而是为了理解代码的真实行为。用测试文档化边界条件的实际输出，比用注释描述"预期行为"更可靠。纯函数模块是最低成本、最高回报的测试起点——没有 mock、没有 I/O、没有环境依赖。

### 43. 批量任务必须串行化以避免资源竞争  `发生: 2026-06-05` `解决: 2026-06-05`

**现象**：播放列表批量处理时，所有视频线程同时运行。12 个 yt-dlp 进程抢占带宽，GPU 显存不足以加载多个 Whisper 模型，全部 fallback 到 CPU。

**教训**：批量任务的直观实现"全开并行"往往是最差方案。串行执行虽然单个视频更慢，但整体吞吐更稳定可预测。本项目的瓶颈是 GPU 显存（4GB），最多只能跑一个 medium 模型。

### 44. 线程安全的单例要用双检锁  `发生: 2026-06-05` `解决: 2026-06-05`

```python
def _get_model():
    if _whisper_model is not None: return _whisper_model       # fast path
    with _model_lock:                                           # lock
        if _whisper_model is not None: return _whisper_model   # double-check
        # ... 实际加载 ...
```

第一次检查无锁（速度优先），持有锁后二次检查（防止竞态）。不加锁时多个线程同时进入第一次检查，依次获取锁后会重复加载模型。`_model_lock` 一行修复了批处理场景下的 Whisper 模型加载冲突。

**教训**：Python 的 GIL 不保护你的代码。多线程访问共享 mutable 状态必须显式加锁。双检锁模式既保证了线程安全，又避免每次调用都获取锁的开销。

### 48. YouTube 字幕语言优先级必须区分 manual/generated  `发生: 2026-06-10` `解决: 2026-06-10`

### 50. PDF 生成需要跨平台降级链  `发生: 2026-06-10` `解决: 2026-06-10`

### 51. ZIP 打包在内存中完成，无需临时文件  `发生: 2026-06-10` `解决: 2026-06-10`

**现象**：50 条 PDF 批量下载，每条平均 400KB，总计约 20MB。

**解决**：`BytesIO()` + `zipfile.ZipFile(buf, "w", ZIP_DEFLATED)` 在内存中组装 ZIP，完成后 `buf.seek(0)` 直接返回。无需磁盘临时文件，代码更简洁。

**教训**：对于"一次性生成、立即下载"的场景，内存流优于临时文件。只要数据量在合理范围（<100MB），内存处理更简单、更安全（无残留文件）、更快（无磁盘 I/O）。

### 54. RAG 两阶段检索比单纯换模型更有效  `发生: 2026-06-11` `解决: 2026-06-11`

**现象**：bge-m3 (1024d) bi-encoder 检索有时返回"语义相近但无关"的片段——问"梯度下降原理"返回顺带提到"梯度"但实际讲其他内容的段落。

**根因**：bi-encoder 将查询和文档各自独立编码为向量，余弦相似度衡量的是"语义空间距离近"，不是"对这个问题有回答价值"。Cross-Encoder 将 `[query, doc]` 对一起输入模型，能精确判断相关性。

**解决**：两阶段检索——Stage 1 bi-encoder 召回 k×4 候选，Stage 2 CrossEncoder `BAAI/bge-reranker-v2-m3` 精排取 top-k。`src/rag/reranker.py` 懒加载单例，首次调用加载模型（~500MB），之后复用。`search()`/`search_global()` 新增 `use_rerank` 参数，由 `settings.rag_rerank` 控制。

**教训**：向量检索的"语义相似"不等于"问题相关"。Cross-Encoder 虽然比 bi-encoder 慢（每对 ~50ms），但在小候选集（20 个）上重排的额外延迟可忽略（~300ms）。两阶段架构在成本和效果间取得了最佳平衡——recall 阶段用便宜的 bi-encoder 广撒网，precision 阶段用贵的 cross-encoder 精选。

### 61. `mermaid.run()` 异步错误未被捕获导致 DOM 空白  `发生: 2026-07-08` `解决: 2026-07-08`

**现象**：web 页面"思维导图" Tab 显示空白，但同一 `mindmap.md` 文件在 VSCode 中可正常预览。

**根因**：`mermaid.run()` 是异步函数（返回 Promise），但前端 `renderMindmap()` 中 `try-catch` 只能捕获同步异常。当 `mermaid.run()` 渲染失败时，Promise rejection 未被捕获；Mermaid 内部 `runThrowsErrors` 的 `catch` 块静默处理错误（不抛到外层），但 DOM 中的 `<pre>` 元素已被清空。

**解决**：改用 `mermaid.render()`（同步返回 SVG 字符串），配合 `async/await` 让 `try-catch` 能真正捕获错误。同时修改两处调用点（历史记录加载 + SSE done 回调）为 `async` 函数并 `await renderMindmap()`。

**教训**：
1. `mermaid.run()` 和 `mermaid.render()` 是不同的 API。`run()` 扫描 DOM 中的 `<pre class="mermaid">` 并替换为 SVG，是异步的；`render()` 直接渲染文本返回 SVG 字符串，是同步的。
2. `try-catch` 只能捕获同步异常。异步函数（返回 Promise）的错误必须用 `.catch()` 或 `async/await` 捕获。
3. 第三方库的异步 API 要仔细阅读文档。Mermaid 10 的 `run()` 是 Promise-based，但示例代码常省略 `await`，导致初学者误以为是同步的。
