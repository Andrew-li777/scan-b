## 一、架构评估 — 85/100

### 优点

**1. 管道分层清晰**。`models.py` 定义数据契约 → 各模块独立实现 → 松耦合。Whisper 转录和 API 字幕都输出 `SubtitleEntry[]`，后续管道对来源完全透明。这是项目最正确的架构决策。

**2. 提取器插件化**。`BaseExtractor` + `match()/extract()` + 注册器，加新平台只需一个文件。YouTube 和 Bilibili 的实现质量差距明显（Bilibili 因反复修复更健壮），但接口一致。

**3. 回退优于单点**。字幕提取三级回退（API → yt-dlp → Whisper），Whisper 模型加载三级回退（medium GPU → small GPU → small CPU），Bilibili 音频下载双通道（yt-dlp → playurl API）。每一层都有兜底。

**4. SSE 长任务通信**。5 种事件类型覆盖所有状态，900s 超时，线程安全 Queue 解耦。架构正确的实时通信选型。

**5. 本地优先**。ChromaDB 嵌入式、diskcache SQLite 后端、faster-whisper 离线运行。零外部服务依赖（除了 LLM API），没有 Docker、Redis、PostgreSQL 运维负担。

### 问题

**1. server.py 承载过重**。501 行中混合了路由定义、业务逻辑、文件 I/O、历史双目录扫描、keypoints 表格解析。分析管道中的 `run()` 函数 180+ 行，包含字幕提取 → 预处理 → 分析 → 翻译 → 输出 → RAG 的全流程。理想情况下 `server.py` 应该只做路由，管道逻辑抽到独立的 pipeline 模块。

**2. 全局变量**。`_whisper_model`、`_device`、`_compute_type`、`_model_size`（transcriber.py）、`_COOKIE_STR`（bilibili.py）、`SSE_EVENTS`（server.py）、`_cache_dir`、`_TEMP_VIDEO_DIR`、`_OUTPUT_DIR`。每个都是合理的懒加载/单例，但都缺乏生命周期管理。测试时需要 mock 或重置这些状态。

**3. 无配置热重载**。`.env` 变更需要重启服务。Whisper 模型大小、VAD 参数、翻译阈值都硬编码。

**4. 错误处理粒度粗**。23 处 `except Exception` 均为静默吞掉或打印后继续。适合"尽力而为"的分析场景，但调试困难的错误（如 Whisper 显存不足）没有区分处理。
