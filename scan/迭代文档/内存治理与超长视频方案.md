# 内存治理与超长视频方案

> 服务器约束：**3.8GB RAM + 2GB swap**，安全线 **3.05GB**（超此线 OOM 风险高）。
> scan 常驻服务与其他服务（translate-web 等）共存，必须控制单任务峰值与任务后回落。
> 本文件记录 2026-08~09 的内存治理过程与结论。

---

## 一、治理前的问题

| 问题 | 表现 | 内存影响 |
|---|---|---|
| 长视频转录峰值 | 2h+ 视频解析内存持续攀升 | 接近/触及 OOM |
| RAG 索引常驻 | 任务完成后常驻 ~1.6GB 不回收 | 基线内存永久抬高 |
| Whisper 模型不释放 | 任务后 RSS 不回落 | 模型内存长期占用 |
| swap 滞留 | VmSwap 累积不降（如 74MB）| 长期运行后可用内存减少 |

## 二、四项治理措施

### 1. 长音频分段转录（峰值控制）

```
音频时长 > whisper_chunk_seconds(600s)
  → 按 600s 切片（相邻重叠 whisper_chunk_overlap=2.0s 防边界丢字）
  → 逐段转录 → 拼接（时间戳偏移校正）
```

**为什么有效**：Whisper 峰值内存 ∝ 单段音频长度，切段后每段独立，峰值与音频总长解耦。

**实测**（2h52m 视频，10355s）：
- 峰值 `mem_used = 2.96GB`（安全线内），scan 进程 RSS 峰值 2.53GB
- 全程 **swap 零增长**（74MB 保持不变）
- 总耗时 46 分钟

### 2. RAG 总开关（常驻内存）

`rag_enabled: bool = False` —— 关闭后 `pipeline.py` 跳过 build_index / index_global。

- **省 ~1.6GB 常驻内存**（bge-m3 嵌入模型 + 向量库）
- 主流程（字幕提取 → 转录 → LLM 分析 → 输出 → 成品）**完全不依赖 RAG**
- 恢复方式：改 True + 重启（代价是常驻内存回来）

### 3. Whisper 模型释放（任务后回落）

`transcribe()` 的 `finally` 块显式释放模型引用 → 任务后 RSS 回落至 **~0.3GB**。

### 4. VmSwap 清零点

Linux 不主动换回已换出页 → 重启 scan 服务清零。**swap 只增不减是正常现象，不是泄漏**。

---

## 三、诊断方法论（复用价值高）

判断「真内存泄漏」还是「正常保留」，用三重证据：

| 手段 | 命令 | 判读 |
|---|---|---|
| 模型是否卸载 | `grep whisper /proc/<pid>/maps \| wc -l` | 0 = 已卸载 |
| 内存构成 | `cat /proc/<pid>/smaps` 聚合 | 匿名堆（Python 对象/glibc 保留）vs 文件映射（模型/so） |
| 线程状态 | `py-spy dump --pid <pid>` | 全 idle = 非模型在工作 |

**关键结论**：CPython + glibc 不归还已 free 的堆给 OS（保留供复用），所以 RSS 高于「活跃对象」是**固有限制**，不是泄漏。判定泄漏要看：多次任务后是否**单调递增**、VmSwap 是否持续涨。

---

## 四、当前内存基线

| 指标 | 数值 |
|---|---|
| scan 空闲 RSS | ~1.07GB（Python 运行时 + 保留堆 + chromadb 残余）|
| scan 任务峰值 RSS | ~2.53GB（长视频，分段转录）|
| 任务后回落 | ~0.3GB（模型释放后）|
| 系统 used / available | ~1.46GB / ~2.45GB（空闲态）|
| swap | 74MB（零增长）|

## 五、注意事项

- **勿同时跑多重型任务**（scan 解析 + translate 全书重译）→ 内存叠加易 OOM
- 长视频解析前建议确认 available > 1.5GB
- 若未来要开 RAG，需重新评估基线（+1.6GB）
